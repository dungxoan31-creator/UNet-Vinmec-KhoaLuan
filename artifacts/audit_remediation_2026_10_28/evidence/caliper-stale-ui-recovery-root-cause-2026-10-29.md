# Caliper stale-retry UI recovery — 2026-10-29

- Root cause: `sendPendingRegionCaliper()` treated any HTTP 200 payload with `current=false` as a retryable error. The server was correctly reporting that an idempotently replayed caliper had been superseded, but the UI retained that request as pending and offered only the same retry. `saveSelectedRegionCaliper()` blocked new measurements while that pending request remained.
- Fix: recognize `current=false` as a completed-but-stale save result. Clear the pending request, hide retry, and reload the active region context so the current D1/D2 values are hydrated. Stale review/region state remains gated by the CDSS panel and requires a fresh region snapshot.
- Live integration evidence: the isolated browser/API/SQLite test lets the real backend commit D1 while the response is dropped, writes a newer D1 through a second real API call, retries the original idempotency key and receives `current=false`, verifies the browser reloads the newer request ID, then verifies the doctor can save the next revision. Only the lost response is fault-injected; successful API responses come from the backend.
- Verification: `npm test` 118 passed/0 failed; JavaScript syntax-check 53 modules; roundtrip E2E PASS, two synthetic images, three-page PDF, zero page errors; safety E2E PASS (18 checks); workstation E2E PASS (1440/1024/768/390 viewports, zero unexpected clinical writes, zero page/runtime errors).
- Clinical measurement accuracy, PostgreSQL behavior, and hospital workflow remain unverified/blocked. This is a UI recovery regression test, not clinical validation.
